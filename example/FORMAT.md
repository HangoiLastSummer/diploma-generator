# Формат входа генератора ВКР — v0.2

Главное: **ты пишешь только смысл, генератор отвечает за всё, что можно посчитать.** Сам ничего не нумеруешь (главы, рисунки, таблицы, листинги, формулы, источники, приложения), не выделяешь курсивом латиницу, не ставишь тире и «ёлочки», не верстаешь титульник и оглавление. Отсюда три вида входа:

| Файл | Что в нём | Почему такой формат |
|---|---|---|
| `diploma.yaml` | титульник, задание, аннотация, аббревиатуры, порядок файлов | короткие структурированные поля, удобно валидировать |
| `sources.yaml` | список источников в виде полей | описание по ГОСТ генератор собирает сам |
| `chapters/*.md` | текст | 60 страниц прозы удобнее всего писать в Markdown |

## Структура проекта

```
my-vkr/
  diploma.yaml
  sources.yaml
  chapters/
    intro.md            # введение (без заголовка: он фиксированный)
    1-analysis.md       # глава 1
    2-design.md         # глава 2
    3-impl.md           # глава 3
    conclusion.md       # заключение
  appendix/
    user-guide.md       # приложение А, руководство пользователя
  img/
  code/
```

## diploma.yaml

Всё, что одинаково для кафедры (вуз, институт, факультет, кафедра, зав. кафедрой, направление, профиль, город), лежит во встроенном профиле `pgu-povt` и здесь не пишется. Любое поле профиля можно переопределить.

```yaml
profile: pgu-povt
year: 2027

student:
  name: Иванов Иван Иванович          # дательный падеж для задания склоняется сам
  # name_dative: Иванову Ивану Ивановичу   # переопределение, если склонилось криво
  group: ИТ23ДР62ПИ

supervisor:
  name: Кирсанова Алла Владимировна
  degree: канд. пед. наук               # «к.п.н.» будет исправлено на это автоматически
  title: доцент

topic: Разработка программной платформы для управления | жизненным циклом данных
# «|» — ручной перенос строки темы на титуле; без него строки разбиваются сами,
# короткие слова (в, и, не, для…) к концу строки не прилипают

order: { number: 354-ОП, date: 2027-03-17 }   # приказ об утверждении темы
deadline: 2027-06-12
task:
  issued: 2027-03-17
  input_data: техническая документация по разработке клиент-серверных приложений, …
  questions: разработать программную платформу для …
  extra: расчёт себестоимости от внедрения результатов

annotation:
  ru: |
    В данной работе разработана серверная платформа RAGManager, …
  en: |
    This paper describes the development of the RAGManager server platform, …

defaults:
  accessed: 2027-03-20  # дата обращения к сайтам, если у источника не указана своя

abbreviations:          # из этого же списка строится «Перечень условных обозначений»
  ПО: программное обеспечение
  СУБД: система управления базами данных
  API: программный интерфейс приложения

content:
  intro: chapters/intro.md
  chapters:
    - chapters/1-analysis.md
    - chapters/2-design.md
    - chapters/3-impl.md
  conclusion: chapters/conclusion.md
  sources: sources.yaml
  appendices:
    - { file: appendix/user-guide.md, kind: user-guide }   # свой титульник и оглавление
    - { file: appendix/b-listings.md, title: Исходный код модуля поиска }
```

## Текст глав (Markdown)

### Заголовки

```markdown
# Исследование и анализ предметной области        → 1 ИССЛЕДОВАНИЕ И АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ
## Описание поставленной задачи, ее обоснование   → 1.1 Описание поставленной задачи, ее обоснование
### Требования к входным данным                   → 1.1.1 Требования к входным данным
#### Входные данные и форматы                     → курсивный псевдозаголовок без номера (B9)
```

Номера не пишешь. Если в файле один `#`, файл — одна глава.

### Ссылки на рисунки, таблицы, листинги, формулы, приложения

Слово в нужном падеже пишешь сам, генератор подставляет только номер. Склонять ничего не нужно, а валидатор проверяет, что перед меткой стоит подходящее слово.

```markdown
Диаграмма вариантов использования представлена на рисунке @fig:usecase.
Классы приведены в таблице @tbl:classes, метод загрузки — в листинге @lst:upload.
Себестоимость рассчитывается по формуле @eq:cost.
Полный код приведен в приложении @app:listings.
```
→ «на рисунке 2.4», «в таблице 2.1», «в листинге 3.2», «по формуле (3.1)», «в приложении Б».

### Рисунок

```markdown
![Диаграмма вариантов использования](img/usecase.png){#fig:usecase}
```

Подпись — это alt-текст. `width=80%` — доля ширины текста (по умолчанию натуральный размер, но не шире поля). В руководстве пользователя подпись можно оставить пустой: `![](img/x.png){#fig:x}` → «Рисунок А.3». Масштаб до ширины поля, пустые строки по 12 pt, «Рисунок 2.4 – …», проверка «ссылка до рисунка», «пункт не заканчивается рисунком» — всё автоматически.

### Таблица

```markdown
Таблица: Классы программного продукта {#tbl:classes}

| Название класса | Назначение |
|---|---|
| BaseEntity | Базовый класс для всех сущностей домена |
| Document | |
```

Многоуровневая шапка — несколько строк до разделителя `|---|`. Объединение ячеек: `<` — слить с ячейкой слева, `^` — с ячейкой сверху:

```markdown
| Название класса | Назначение | Члены класса    | <      |
| ^               | ^          | Поля и свойства | Методы |
|---|---|---|---|
| BaseEntity      | Базовый класс | Id           | Equals |
```

Пустая ячейка (или одиночный дефис) превращается в «–». Большая шапка: `{#tbl:x header=numbered}` — графы нумеруются, на продолжении повторяется только строка номеров. Если таблица разорвётся между страницами, генератор сам повторит шапку и вставит «Продолжение таблицы 2.1».

### Листинг

````markdown
```csharp {#lst:upload caption="Метод загрузки документа"}
public async Task<Guid> ExecuteAsync(Stream fileStream, Guid libraryId)
{
    ...
}
```
````

Листинг длиннее половины страницы (≈ 26 строк с учётом переносов) валит сборку с подсказкой «вынеси в приложение».

### Формула

```markdown
$$ C = \sum_{i=1}^{n} c_i $$ {#eq:cost}

где $c_i$ – стоимость i-го компонента, руб.;
$n$ – число компонентов.
```

Формула в LaTeX превращается в формулу Word (OMML) с номером (3.1) у правого края. Абзац, начинающийся с «где» сразу после формулы, становится пояснением: без отступа, каждый символ с новой строки.

### Источники

```markdown
Подход описан в работе [@martin2017], конкретная оценка — в [@lewis2020, с. 9461].
```
→ «[6]», «[5, с. 9461]». Номера зависят от порядка списка (по умолчанию алфавит).

### Списки

| Пишешь | Получаешь | Пункты |
|---|---|---|
| `- пункт` | `- пункт` | со строчной, `;`, последний `.` — исправляется само |
| `1. Пункт` | `1. Пункт.` | с прописной, точка в конце |
| `1) пункт` | `а) пункт`, вложенный — `1) пункт` | со строчной, `;` |

### Комментарии

`<!-- ... -->` генератор пропускает. В них заготовка хранит задание на подраздел и целевой объём, а ты и Claude — свои пометки.

### Что запрещено в тексте

- `**жирный**` в обычном тексте (C11): для выделения терминов есть `*курсив*`, для подзаголовков — `####`;
- номера глав/рисунков/источников, написанные руками (`Рисунок 2.1`, `[3]`): валидатор ловит их и просит заменить меткой;
- аббревиатура (2+ заглавные буквы подряд), которой нет в `abbreviations`.

## sources.yaml

```yaml
martin2017:
  type: book
  authors: [Martin, R. C.]
  title: "Clean Architecture: A Craftsman's Guide to Software Structure and Design"
  city: Boston
  publisher: Prentice Hall
  year: 2017
  pages: 432

lewis2020:
  type: article
  authors: [Lewis, P., Perez, E., Piktus, A.]
  title: Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks
  journal: Advances in Neural Information Processing Systems
  year: 2020
  volume: 33
  range: 9459–9474

docker-docs:
  type: web
  title: Документация Docker
  url: https://docs.docker.com/
  accessed: 2027-03-15          # если не указано — дата из defaults.accessed
  checked: true                 # источник реально существует и проверен человеком (см. CLAUDE.md)
```

Из `type` и полей собирается строка по ГОСТ Р 7.0.11-2011 (см. RULES.md, I4). Язык (отечественный/иностранный) определяется по алфавиту, год даёт давность: этого хватает, чтобы заполнить бланк аннотации (L2).

## Команды

```
vkr init --type web          # проект из шаблона: CLAUDE.md, заготовки глав под тип работы (J2), context/
vkr check                    # валидатор, без вёрстки, ~секунда
vkr check --format json      # то же для Claude: [{rule, severity, file, line, message, hint}]
vkr fix                      # безопасные правки (тире, кавычки, пунктуация списков) пишутся прямо в .md
vkr stats                    # слова по разделам против целевого объёма (≈ 270 слов на полную страницу)
vkr build -o vkr.docx        # валидатор → билдер → цикл вёрстки → vkr.docx + report.md
vkr preview --pages 12-14    # PNG страниц: Claude может посмотреть вёрстку глазами
```

`build` исходники не меняет никогда: все автоисправления на лету и в отчёте. Чтобы они осели в .md (и были видны в git diff), есть `vkr fix`.

`report.md` (и `report.json`) — три раздела: **ошибки** (сборка не прошла), **исправлено автоматически**, **предупреждения**. Каждая запись указывает на файл и строку исходника; предупреждения после вёрстки — ещё и на номер страницы.
